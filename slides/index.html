為什麼要邊想邊做？ReAct 的證據

ReAct 在 2022 年提出：讓 LLM 把推理和行動交錯進行。

  • 推理：建立、追蹤、更新計畫
  • 行動：從外部取得資訊（例如 Wikipedia API）
  • 只推理容易產生幻覺和錯誤傳遞
  • 推理過程看得懂，比較好信任和除錯

絕對成功率提升

ALFWorld+34%
WebShop+10%

比較對象是模仿學習與強化學習方法，而且只用了 1–2 個 in-context 範例。

Workflow vs Agent：流程由誰決定？

Workflow

預先寫好的程式路徑；適合定義清楚、需要可預測的任務。

Agent

LLM 自己動態決定流程與工具；彈性高，但延遲和成本也高。

  • Prompt chaining固定步驟接力，中間可以加關卡檢查
  • Routing先分類，再送到專門的流程
  • Parallelization拆開同時跑，或跑多次再投票
  • Orchestrator-workers中央 LLM 動態拆解、分派、彙整
  • Evaluator-optimizer一個產生、一個評估，循環修正

工具決定 agent 能做什麼

三類工具

Data：查資料、讀 PDF
Action：寄信、更新紀錄
Orchestration：把別的 agent 當工具

ACI：替模型設計介面

工具說明值得像主 prompt 一樣用心寫。Poka-yoke 防呆：模型常用錯相對路徑，改成強制絕對路徑後就不再出錯。

MCP：標準接口

MCP server 公開資料與工具，MCP client（AI 應用）連過去，不用每個資料源都各寫一套整合。

Wiki 來源：tools-and-acimcp

一個 agent 不夠時：多代理

建議先從單一 agent 開始。訊號是邏輯太複雜，或工具太多又彼此重疊（重點是重疊，不是數量）。

Manager 模式

中央 manager 用工具呼叫分派給專門 agent，再彙整結果，自己保有主控權。

例：翻成西、法、義三種語言，各交給一個 agent。

Decentralized 模式

agent 之間用 handoff 單向交棒，把控制權和對話狀態一起交出去。

例：分流 agent 把訂單問題交給訂單管理 agent。

什麼時候真的需要 agent？

先找最簡單的解法。Agentic system 是用延遲和成本換表現，很多時候把一次 LLM 呼叫優化好就夠了。

複雜決策

需要細緻判斷和處理例外

例：退款審核

難以維護的規則

規則多到難以更新

例：供應商資安審查

非結構化資料

要讀文件、跟人對話

例：房屋保險理賠

都不符合？用確定性的解法可能就夠了。規則引擎像檢查清單，agent 像經驗豐富的調查員。

風險與 guardrails

agent 的挑戰

  • context 長度有限
  • 長期規劃困難，遇到意外很難調整
  • 自然語言介面不可靠，輸出可能格式錯誤
  • 錯誤會一步步累積（compounding errors）
  • 在專業領域，LLM 不一定能正確評估自己

分層防護

  • Relevance / Safety classifier、PII filter、Moderation
  • 工具依風險分低、中、高（唯讀或可寫？可不可逆？）
  • 交給人類：失敗次數超過門檻、高風險動作（大額退款、付款）
  • 在沙盒環境中大量測試
